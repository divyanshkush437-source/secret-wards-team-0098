# Break Indian de-identifiers before attackers do

The hardest realistic test cases for an Indian hospital de-identification pipeline are collisions, not exotic tricks. These are strings that mean two things at once. A 12-digit SNOMED CT code passes the same Verhoeff checksum as an Aadhaar number. A 14-digit `YYYYMMDDhhmmss` timestamp has the shape of an ABHA number. "C/O" can mean "complaint of" or "care of". "Asha" can be a patient, an ASHA worker or the word "hope". "Sitapur" is a district, and its name contains a deity who is also a common given name. Layered on top of those are three things that published benchmarks never test: Devanagari digits, homoglyphs and encoded payloads (base64, percent, HTML and JSON escapes) hidden in FHIR extensions, narrative and attachments. The third layer is the one no detector catches. Name-free records still re-identify people through the public electoral roll, which lists name, relative's name, age, sex and house number for every voter. Clean-text recall says nothing about that. The best published tools already reach **99.46–99.92% recall** on clean English notes ([Norgeot et al. 2020](https://link.springer.com/10.1038/s41746-020-0258-y)), yet a model trained on non-Indian notes performed poorly on real Indian discharge summaries ([Singh et al., arXiv 2407.05887](https://arxiv.org/html/2407.05887v1)). A "hardest-possible" Track 3 dataset therefore has to be synthetic, multi-format and adversarial by construction. Its scorer must report five separate axes: detection recall per obfuscation class, residual re-identification risk against a simulated voter-roll attacker, date integrity, linkage and pseudonym consistency, and clinical utility. No single F1 score can be allowed to hide a leak or reward redacting everything.

## Identifier checksums collide with clinical codes, timestamps and lab values

Aadhaar is the right place to start because it looks the most "solved". It is 12 digits, the first digit is never 0 or 1, and the last digit is a Verhoeff check digit. Microsoft Presidio's recognizer scores a bare 12-digit match at only **0.01**. It accepts hyphen, space or colon separators and relies on the context words "aadhaar" and "uidai" plus a Verhoeff check and a non-palindrome check ([Presidio source](https://raw.githubusercontent.com/microsoft/presidio/main/presidio-analyzer/presidio_analyzer/predefined_recognizers/country_specific/india/in_aadhaar_recognizer.py); [Microsoft Purview](https://learn.microsoft.com/en-CA/purview/sit-defn-india-unique-identification-number)). The trap is that **SNOMED CT identifiers also end in a Verhoeff check digit** ([SNOMED spec 6.4](https://docs.snomed.org/snomed-ct-specifications/snomed-ct-release-file-specification/snomed-ct-identifiers/6.4-check-digit)). A long SNOMED extension ID that starts with 2–9 can pass every Aadhaar validator, and only context can tell them apart. The test set should put Verhoeff-valid synthetic Aadhaar strings with no context next to SNOMED codes in their native context ("SNOMED: …"). It should also include near-misses, where one changed check digit or one transposition makes Verhoeff fail but an "Aadhaar No." label is still present. That case forces an explicit policy choice, because a mistyped Aadhaar is still identifying. UIDAI's official masked form shows only the last four digits (`xxxx-xxxx-0127`) ([UIDAI FAQ](https://www.uidai.gov.in/283-faqs/aadhaar-online-services/e-aadhaar/1887-what-is-masked-aadhaar.html)), and attendance systems have used last-four or last-eight fragments ([Wikipedia: Aadhaar](https://en.wikipedia.org/wiki/Aadhaar)), so partial Aadhaar has to be a labelled category. The 16-digit VID is a revocable random number that UIDAI says agencies should not store ([UIDAI VID FAQ](https://uidai.gov.in/284-faqs/aadhaar-online-services/virtual-id-vid/1899-can-an-agency-store-vid.html)). It collides with card numbers and transaction IDs.

The ABHA number is a system-generated **14-digit** number. Each one gets a default address of the form `<14digits>@abdm` (`@sbx` in sandbox), and users can add custom handles such as `ramesh123@abdm` ([ABDM docs](https://kiranma72.github.io/abdm-docs/2-milestone1/abha-number/default-abha-address/index.html)). The ABDM forum gives conflicting validation rules for the handle: one thread says at most 18 characters with one dot or underscore, another reports an API error requiring 4–32 characters, and a third says dots stopped working ([devforum 3956](https://devforum.abdm.gov.in/t/abha-address-validation-constraints/3956); [devforum 5219](https://devforum.abdm.gov.in/t/create-abha-address-validation-issue/5219); [devforum 3546](https://devforum.abdm.gov.in/t/creating-health-ids-with-dot-is-not-working-anymore/3546)). A detector tuned to one rule set will miss handles valid under another. ABHA addresses also look like UPI IDs (`9876543210@ybl`) and emails, and all three are identifying. The common `XX-XXXX-XXXX-XXXX` card layout and a leading "91" could not be confirmed from an official source. The dataset should therefore include hyphenated, plain and non-91 variants, and treat a 14-digit timestamp like `20261126143005` as a hard negative.

Phones are the highest-volume identifier and the easiest to fake. Mobiles are 10 digits starting with 6–9, split XXXXX-NNNNN ([Wikipedia: Mobile numbering](https://en.wikipedia.org/wiki/Mobile_telephone_numbering_in_India)). Landlines always total 10 digits with STD codes of 2–8 digits, and telemarketers get 140-prefixed numbers ([Wikipedia: Telephone numbers in India](https://en.wikipedia.org/wiki/Telephone_numbers_in_India)). Hard positives are grouping drift (`9876 501 234`, `98 76 50 12 34`), prefixes (`091-`, `0`, `(+91)`), numbers spelled out in English or Hindi ("नौ आठ सात…", "nine double eight"), WhatsApp links (`wa.me/91…`) and partial masks (`98XXXXXX34`). Hard negatives are 10-digit lab accession and bill numbers starting with 6–9, 10-digit ESIC IP numbers ([ClearTax](https://cleartax.in/s/esic-number)) and institutional lines such as the AIIMS IVRS number, which some policies may keep ([Deccan Herald](https://www.deccanherald.com/aiims-gives-unique-health-id-numbers-378904.html)). PIN codes are the worst shape collision. They are six digits with a 1–9 lead digit ([Wikipedia: PIN](https://en.wikipedia.org/wiki/Postal_Index_Number)), exactly the shape of a platelet count written in /cumm (`Plt 245000`), an Indian-grouped amount or a DDMMYY date.

The remaining identifiers widen the attack surface rather than deepen it. PAN follows `AAAAA9999A`, and its fourth letter encodes the holder type, with P for individuals ([Wikipedia: PAN](https://en.wikipedia.org/wiki/Permanent_account_number)). That makes `ABCDE1234F`, the canonical form placeholder with an invalid fourth letter D, a useful negative. A GSTIN embeds a PAN. Presidio's voter-ID regex (`[A-Za-z]{3}[0-9]{7}`) also matches drug batch numbers ([Presidio voter recognizer](https://raw.githubusercontent.com/microsoft/presidio/main/presidio-analyzer/presidio_analyzer/predefined_recognizers/country_specific/india/in_voter_recognizer.py)). Its weakest vehicle-plate patterns (`[A-Z]{2}\d{4}`) will fire on PMJAY package codes, such as `SG039A` for cholecystectomy ([Presidio vehicle recognizer](https://raw.githubusercontent.com/microsoft/presidio/main/presidio-analyzer/presidio_analyzer/predefined_recognizers/country_specific/india/in_vehicle_registration_recognizer.py); [NHA HBP 2.0](https://nha.gov.in/img/resources/HBP-2.0-Package-master.pdf)). Driving licences run to 15 characters (state, RTO, year, serial) ([Paytm DL FAQ](https://paytm.com/faqs/drivers-licence/how-many-digits-is-driving-licence-number)), and vehicle plates show up in road-accident MLC notes. UHID formats are institution-specific and undocumented. AIIMS issues them through NIC's e-Hospital system, with Aadhaar linkage optional ([Deccan Herald](https://www.deccanherald.com/aiims-gives-unique-health-id-numbers-378904.html); [Business Standard](https://business-standard.com/article/pti-stories/aiims-writes-to-health-min-for-linking-of-aadhaar-with-uhid-116120701429_1.html)). Official formats for the PMJAY ID, CGHS beneficiary ID, ration card and passport were not verified in this research. The dataset should vary their lengths and must not encode a guessed format as ground truth.

## Indian names, kin chains and villages defeat surname logic

No single given-name/surname model fits India. In Tamil naming, initials stand for village and father, so "R. Kumaresh" becomes "Kumaresh Ramaiah" when written in full. Telugu puts the house name first. Rural Hindi-belt women often take **Devi** or **Kumari** after marriage. Sikh names carry Singh or Kaur, which work as gender markers more than surnames. Marathi women take the husband's name as the middle name ([Wikipedia: Indian name](https://en.wikipedia.org/wiki/Indian_name)). "Muhammad" has a dozen romanizations plus the abbreviations "Md.", "Mohd." and "M." ([Wikipedia: Muhammad (name)](https://en.wikipedia.org/wiki/Muhammad_(name))). Given names can be ordinary or clinical words: Indian twins were named "Corona" and "Covid", and another baby "Sanitiser" ([Al Jazeera](https://www.aljazeera.com/news/2020/04/india-newborn-twins-named-corona-covid-virus-200404093616017.html); [Global News](https://globalnews.ca/news/6846285/baby-named-sanitiser-coronavirus)). The test set should therefore pair each name sense with its non-name sense. Examples are "ASHA Asha Devi ne bataya", "pooja ke baad se bukhar" next to "Pooja ko bukhar", and a sentence where Wilson is the patient's surname, the referring doctor and the name of the disease ("Pt Wilson D'Souza, k/c/o Wilson's disease, ref by Dr. Wilson"), of which only the eponym must survive. The i2b2/n2c2 challenges already found PROFESSION and LOCATION to be the hardest categories in English ([arXiv 1810.06765](https://arxiv.org/pdf/1810.06765)), and Indian villages named after deities and people make LOCATION harder still.

Kinship markers are the most Indian-specific trap. A registration line such as "Sita Devi W/O Ram Prasad S/O Late Shiv Prasad R/O Vill Rampur Post Sitapur" names three people, one of them dead, plus a village and a post office. The person names are deity names, and the place names contain deity names. The abbreviations are ambiguous as well: clinical glossaries list "C/O" as both "complains of" and "care of", and "H/O" as "history of" ([YourDictionary](https://www.yourdictionary.com/articles/medical-abbreviations); [MedicineNet](https://www.medicinenet.com/common_medical_abbreviations_and_terms/article.htm)). The hardest single line puts both meanings side by side, such as "C/O fever x 3 days, C/O Ramesh (bhai) 98xxxxxxxx". "K/C/O", "F/H/O" and "H/O HTN" must survive untouched. Newborns are often registered as "Baby of [mother's name]" before the naming ceremony ([DocuPro](https://docupro.in/blog/birth-certificate-mistakes-in-india-how-to-correct-them-2026)), and names given at birth often change later ([Hindustan Times](https://www.pressreader.com/india/hindustan-times-st-jaipur/20180205/281728384966236)). So "B/O Rekha" has to be redacted as mother's PHI, and "B/O Rekha (Twin I)" and "(Twin II)" are two people.

Transliteration is where linkage and detection fail together. Hunterian, India's official romanization, merges dental and retroflex consonants. Hindi deletes the inherent schwa, so राम is "Ram" in speech while naive transliteration writes "Rama" ([Wikipedia: Hunterian](https://en.wikipedia.org/wiki/Hunterian_transliteration); [Wikipedia: Schwa deletion](https://en.wikipedia.org/wiki/Schwa_deletion_in_Indo-Aryan_languages)). IDinsight found सुनीता recorded as "Sunita" in one dataset and "Suneeta" in another. Off-the-shelf fuzzy matchers produced "unacceptably high rates of false matches", and Latin-optimized distances overstate how far apart Hindi name variants are ([IDinsight](https://www.idinsight.org/article/part-1-whats-in-a-name-combining-datasets-when-unique-identifiers-are-missing/)). Even inside Devanagari, byte-different strings look identical. The precomposed nukta letters U+0958–U+095F are composition exclusions, so NFC turns them into the *decomposed* base-plus-nukta sequence ([Unicode CompositionExclusions](https://www.unicode.org/Public/UCD/latest/ucd/CompositionExclusions.txt)). ZWJ and ZWNJ legitimately choose half-forms or a visible virama and survive normalization ([Unicode Indic FAQ](https://www.unicode.org/faq/indic.html)). A gazetteer keyed on ज़ाकिर in one encoding misses the other unless the pipeline normalizes first. A pipeline that strips every ZWJ will corrupt legitimate Hindi. Each spelling cluster (Srivastava/Shrivastav, Lakshmi/Laxmi/Luxmi, Chaudhary/Choudhury, Vasanti/Basanti, Zakir/Jakir) should therefore be one gold entity across Roman, Devanagari and mixed-script forms such as `Rामप्रसाद` and `Smt.सुनीता`. Romanized Hindi has no standard spelling at all ([PHINC, arXiv 2004.09447](https://arxiv.org/pdf/2004.09447)), and real Hinglish switches script mid-sentence ([COMI-LINGUA, arXiv 2503.21670](https://arxiv.org/html/2503.21670v1)). The only published code-mixed clinical de-id dataset (Chinese-English) found that code-mixed training data mattered ([PMC10853853](https://pmc.ncbi.nlm.nih.gov/articles/PMC10853853)). No Hinglish clinical PHI corpus exists, which is why Track 3 needs one.

Rural addresses have no streets. They are a chain from village through post office, police station (thana), tehsil or block and district to PIN, and the name of each level differs by state: tehsil, taluk, mandal or subdivision. Tehsil and block are separate units that need not coincide ([Wikipedia: Tehsil](https://en.wikipedia.org/wiki/Tehsil)). The hardest address strings repeat one name across levels ("Vill Lalganj, Post Lalganj, Thana Lalganj"). They also use twin-village suffixes (Kalan/Khurd), Hindi labels (ग्राम, जनपद, थाना), landmarks that carry a person's name ("Sharma kirana store ke peeche"), informal city codes (Lko, Knp) and renamed cities (Allahabad/Prayagraj, Gurgaon/Gurugram) that a linker has to treat as one place. These conventions come from domain knowledge rather than a fetched specification and should be checked with clinicians before freezing the gold labels.

## Encodings and hidden fields slip past every published benchmark

Character-level obfuscation works because a regex or tokenizer sees different code points from the ones a human reads. Mimecast defeated a PII filter with Cyrillic look-alike letters, a fullwidth "@", a Roman-numeral "ⅼ" and a non-breaking hyphen inside a phone number. The original text was redacted and the disguised version passed through untouched ([Mimecast](https://www.mimecast.com/blog/5-keystrokes-that-defeat-a-privacy-filter/)). Unicode TR39 gives the fix: build a confusable "skeleton" (NFD, drop default-ignorables, map each character to its prototype) and flag mixed number systems. TR39 also allows ZWJ and ZWNJ only in narrow Indic conjunct contexts ([Unicode TR39](https://www.unicode.org/reports/tr39/)). Devanagari digits cut both ways. Python's `\d` matches any Unicode Nd digit unless `re.ASCII` is set ([Python re docs](https://docs.python.org/3/library/re.html)), so `९८७६५४३२१०` is found by one engine and missed by `[0-9]`-style or ASCII-only engines. Even when found, it breaks validators that expect ASCII. The digit tests therefore need all ten Indic digit systems plus Urdu Arabic-Indic, and mixed strings such as `98७६543210`. Typo and synonym perturbations alone already "drastically reduce" biomedical BERT NER performance ([Araujo et al., arXiv 2004.11157](https://arxiv.org/abs/2004.11157v1); [arXiv 2109.11308](https://ar5iv.labs.arxiv.org/html/2109.11308)).

Encoding is a larger blind spot, and no clinical de-id paper found in this research measures recall on encoded PHI. Security practice says to canonicalize to the simplest form iteratively before inspection, because double encoding (`%2520`) defeats filters that decode only once ([OWASP Double Encoding](https://owasp.org/www-community/Double_Encoding); [CAPEC-120](https://capec.mitre.org/data/definitions/120.html)). FHIR R4 makes this concrete: `Attachment.data` is base64 and "not constrained", so it can carry any content type ([HL7 FHIR R4 Datatypes](https://hl7.org/fhir/R4/datatypes.html)). Narrative may embed `data:` URIs and must use Unicode characters rather than `&nbsp;`-style entities ([HL7 FHIR R4 Narrative](https://hl7.org/fhir/R4/narrative.html)). The dataset should carry the same synthetic PHI in several wrappers: plain base64 (`UmFtZXNoIEt1bWFyIDk4NzY1NDMyMTA=`), gzip-then-base64 (starting with the `H4sI` gzip magic), percent and double-percent encoding inside `Attachment.url` and `meta.source`, decimal and hex HTML entities for Devanagari (`&#2352;&#2350;&#2375;&#2358;`), JSON `\u` escapes in which a grep of raw bytes sees no digits at all, quoted-printable with a soft line break inside the phone number, hex, and nested chains that test both fixed-point decoding and a depth cap. Decoys, base64-looking ward codes that decode to nothing, keep false-positive control honest.

FHIR holds PHI in places most tools skip. Narrative with status "additional" can contain human-authored content that is not in the structured fields. Narrative is also supposed to summarize referenced resources, which pulls Patient and Practitioner PHI into `text.div` ([HL7 FHIR R4 Narrative](https://hl7.org/fhir/R4/narrative.html)). Microsoft's open-source FHIR anonymizer states that **"Anonymization of fields within Extensions is not supported"**. Its sample config simply redacts every Extension, and it calls the HIPAA catch-all identifier type "unspecific and hence not considered" ([microsoft/Tools-for-Health-Data-Anonymization](https://github.com/microsoft/Tools-for-Health-Data-Anonymization/blob/master/docs/FHIR-anonymization.md)). IHE says freeform text cannot be assured anonymous ([IHE De-Id Handbook](https://profiles.ihe.net/ITI/DeId/fhir-example.html)), and HL7's DARTS example just drops the narrative ([HL7 DARTS](https://build.fhir.org/ig/HL7/fhir-darts/implementation.html)). A single hardest Bundle should therefore hide PHI in `extension.valueString` (mother's name), in extension URLs themselves, `identifier.system` URLs, resource ids (`Patient/ramesh-kumar-9876543210`), `Reference.display` with an embedded "S/o", `meta.tag.display`, contained RelatedPersons, `Annotation.authorString`, `Communication.payload.contentString`, a `tel:` link in markdown and a base64 discharge summary in `DocumentReference`. Its narrative should disagree with its structured fields.

Parser disagreement is itself a leak channel. Python's JSON library keeps the last of two duplicate keys, while Go, rapidjson, Java json-iterator and others keep the first. ujson truncates lone surrogates, so `"phone"` and `"phone\ud800"` collide. Many parsers accept comments that strict scanners reject. Huge numbers decode to 0, Infinity or strings depending on the library ([Bishop Fox](https://bishopfox.com/blog/json-interoperability-vulnerabilities)). A file with `{"name":"REDACTED","name":"Ramesh Kumar"}` tests whether the scanner and the downstream consumer read the same value. CSV and file-level traps complete the set: PHI in file names, header cells and JSON keys, formula cells (`="98765"&"43210"`), Excel-mangled `9.87654E+09`, ragged rows whose extra unnamed column holds the phone, multi-line quoted cells, mid-file BOMs, UTF-16LE (where byte-level regexes fail), wrong extensions, deep nesting, a single huge line with PHI straddling a chunk boundary, and zip path traversal. OWASP warns that logs and stack traces leak sensitive data ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). The scorer should plant unique canary strings and grep outputs, logs and temp directories after every run.

## Name-free records still re-identify through India's voter rolls

Detection recall does not measure privacy. In Sweeney's analysis of 1990 US Census data, 5-digit ZIP, gender and date of birth were enough to make **87%** of Americans likely unique ([Sweeney 2000](https://dataprivacylab.org/projects/identifiability/paper1.pdf)). Golle's re-analysis on 2000 Census data found about **63%** ([Golle](https://crypto.stanford.edu/~pgolle/papers/census.html)). Over 96% of about 2,800 patients were unique on their diagnosis-code sets ([Loukides et al., PMC2995712](https://pmc.ncbi.nlm.nih.gov/articles/PMC2995712)). Four spatio-temporal points single out 95% of mobility traces ([de Montjoye et al., PMC3607247](https://pmc.ncbi.nlm.nih.gov/articles/PMC3607247)). Rocher et al. estimate 99.98% correct re-identification with 15 demographic attributes, and show that releasing only a sample barely helps ([PMC6650473](https://pmc.ncbi.nlm.nih.gov/articles/PMC6650473)). The steelman deserves weight. El Emam's review found that only 2 of 14 published attacks targeted data de-identified to an existing standard, and the one health attack among them re-identified just **0.013%** of records ([PMC3229505](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC3229505/)). Standards-based de-identification therefore works, but only if the release actually meets the standard, and India has no HIPAA-style 20,000-population rule for PINs or villages.

India's equivalent of the US voter list is the published electoral roll. Each entry lists elector name, relation type and relation name (father, mother or husband), age, gender, house number and EPIC number, published per polling-booth "part" ([ECI Form 6](https://voterportal.eci.gov.in/guidelines/Form-6_en.pdf); [ECI roll report format](https://voters.eci.gov.in/eroll/asd/2026/u02/1/uncollectable_elector_report_ac1_part460_ENG.pdf)). The relation-name column joins directly to the "S/o" and "W/o" strings in hospital records. A pipeline that redacts the patient's name but keeps "W/o Suresh Yadav, H.No. 14, Village Kheri" has effectively published the patient. The attacker harness should therefore generate a synthetic roll per part, join on {age ±1, sex, village}, and plant the hard cases. These include a village with fewer than 300 residents, a 103-year-old, a zero-day neonate whose DOB equals admission, a single rare diagnosis in one village, and visit sequences known from a few public facts ("admitted the week after Diwali for dengue, readmitted 12 days later"). Pseudonyms need their own attacks. Unsalted hashes over small spaces such as phone numbers are reversible in under 100 seconds on consumer hardware ([messenger contact-discovery study](https://bibsonomy.org/bibtex/fc1c71058ae879016b8c93f716e35612); [AEPD-EDPS](https://edps.europa.eu/sites/edp/files/publication/19-10-30_aepd-edps_paper_hash_final_en.pdf)). A test should plant SHA-256 of 10-digit mobiles and Aadhaar numbers, structured UHIDs that leak year and department, and two releases of one cohort with different keys but shared date offsets. India's regulatory bar is unsettled. The draft ABDM Health Data Management Policy defines anonymisation as irreversible and allows public release only of anonymised *and aggregated* data ([ABDM HDM Policy](https://abdm.gov.in:8081/uploads/health_management_policy_bac9429a79.pdf)). The DPDP Act has no separate health-data category ([Mondaq](https://www.mondaq.com/india/healthcare/1722484/health-data-the-dpdp-actnavigating-indias-healthcare-privacy-frontier)). No published study measures {age, sex, village} uniqueness in India, so the harness's numbers will be the first of their kind and should be reported as such.

Linkage cuts both ways. A false merge pools two people's PHI and dates. A missed link breaks pseudonym and date-offset consistency, so one patient's timeline splits. The hardest planted cases are twins with names one letter apart, a father and son with the same name in one house, five relatives sharing one phone, a married woman whose surname and relation name both change (the voter form itself switches from father to husband ([Bihar Form 6](https://ceoelection.bihar.gov.in/forms/Form-6-English.pdf))), re-registration under a new UHID, age drift ("45 yrs" in 2022, "47 yrs" in 2025), DD/MM swaps, and a transitive chain A≈B≈C≈D that single-link clustering collapses. Pairwise F1 is overly optimistic and dominated by large clusters. B-cubed and Generalized Merge Distance expose cluster damage ([Barnes, arXiv 1509.04238](https://arxiv.org/pdf/1509.04238); [Binette et al., arXiv 2404.05622](https://arxiv.org/html/2404.05622v1)), and F-measure weights differ between linkage methods ([Hand & Christen 2018](https://spiral.imperial.ac.uk/handle/10044/1/46235)).

Dates are where parsing and privacy meet. Consistent per-patient date shifting preserves intervals, but it remains pseudonymisation. In one Belgian/Dutch corpus, **91.4%** of notes were written Monday–Friday, and weekday and holiday patterns narrow down the candidate offsets. The authors recommend offsets of more than a year per patient ([MedDeID, arXiv 2609.10049](https://arxiv.org/html/2609.10049)). MIMIC-III deliberately kept weekday and season ([PhysioNet](https://physionet.org/content/mimiciii/1.4/)), and shift-and-truncate drops a 366-day boundary window because study edges leak the true calendar ([MSDW](https://labs.icahn.mssm.edu/msdw/wp-content/uploads/sites/350/2021/11/Truncate_and_Shift.pdf)). Indian festivals are public anchors: "Diwali ke din patakhe se jala" next to a shifted date reveals the offset. The parser tests need `03/04/2025` (3 April in India), two-digit years, "Jan-26", Hindi month names, Vikram Samvat ("चैत्र शुक्ल प्रतिपदा संवत 2082"), Hijri ("12 Ramzan 1446"), 29 February shifted into a non-leap year, and IST `+05:30` timestamps. Things that look like dates but must not be touched include BP `120/80`, dosing `1-0-1`, `1/2 tab` and IP numbers like `12/2025/334`. Hinglish relative expressions such as "3 din pehle se" and "kal raat" are durations, not PHI, and must not be rewritten.

## Score five axes so no system wins by redacting everything

The dataset should be generated from a synthetic patient graph rather than written note by note. That way every surface form traces back to a gold entity, a gold person and a gold true date. Each synthetic patient carries a native-script name, its transliteration cluster, relatives, a rural or urban address chain, identifiers with valid and near-miss checksums, and a timeline. Each record is rendered several times: FHIR R4 Bundles with PHI in every location listed above, CSV/TSV exports with header, formula and ragged-row traps, JSON and JSONL with duplicate keys and escapes, and free-text discharge summaries, nursing notes and WhatsApp messages in English, Devanagari Hindi and Hinglish. A seeded obfuscation layer then applies one transform family per copy (homoglyph, Indic digits, zero-width, bidi, number words, OCR confusion, base64, gzip+base64, percent, double percent, HTML entities, JSON escapes, quoted-printable, nesting), so recall can be broken down by attack class. Every sample should be labelled at character offsets *in the decoded canonical text* and mapped back to raw byte spans, so the scorer can tell "found after decoding" apart from "missed". An equal number of must-preserve spans (drug strengths, dosing grids, vitals, labs in /cumm and lakh, ICD/LOINC/SNOMED codes, PMJAY packages, eponyms, K/C/O shorthand) keeps the test from rewarding over-redaction. Specific code values taken from background knowledge must be verified against the official code systems before they become ground truth.

| Axis | Primary metric | Pass condition / why |
|---|---|---|
| Detection | Character-level PHI recall per category and per obfuscation class; strict-entity P/R; F2 | Any surviving gold character counts as a leak (MedDeID-style core recall ([arXiv 2609.10049](https://arxiv.org/html/2609.10049))); report the leak count, not just a rate |
| Residual risk | Share of k=1 records and correct re-identifications by the voter-roll attacker, released ÷ raw; pseudonym-inversion success; cross-release join success | Recall alone does not estimate re-identification probability ([arXiv 2609.10049](https://arxiv.org/html/2609.10049)) |
| Date integrity | Parse accuracy by format family; within-patient interval error = 0; invalid dates, order violations, events before DOB; candidate-offset entropy after festival/weekday constraints | Shifting must preserve the clinical timeline without leaking the offset |
| Linkage consistency | Pairwise F0.5, B-cubed P/R, impure-cluster count, max cluster size, per-trap pass/fail; same person gets the same pseudonym and offset | Precision-weighted because false merges leak and corrupt records |
| Utility | Exact preservation of planted clinical spans; numeric drift = 0; downstream extraction parity | Plotted against privacy so blanket redaction scores badly |
| Robustness | No crash or silent skip on malformed input; canary absent from outputs, logs and temp files; scanner and consumer agree on duplicate keys | Parser divergence and logs are real leak paths |

The leaderboard should report the axes separately and gate on hard failures before any composite score. A system that leaks a canary, merges twins, leaves an S/o relative name next to a village, or changes a dose should fail that trap whatever its average. i2b2 practice shows strict-entity scores running about 3–4 points below token scores ([Dernoncourt et al.](https://groups.csail.mit.edu/medg/ftp/psz-papers/2016%20Dernoncourt.pdf)). Character-level recall is the honest privacy number, and strict entities remain useful for pseudonymization quality. The download package should have a public development split and a hidden test split, with fresh generator seeds for the hidden split so that systems cannot memorize surface strings. It should ship an `obfuscation_class` field on every gold span, a `must_preserve` label set, the synthetic electoral-roll tables and attacker scripts, and a manifest of each file's intended parse, so that "wrong extension" and "BOM" cases have defined expectations.

## Conclusion

The research points to one design principle: a hard Indian de-identification test is hard because it is *ambiguous*, not because it is large. Verhoeff collisions with SNOMED, ABHA-shaped timestamps, PIN-shaped platelet counts, C/O and H/O, deity-named villages and festival-dated injuries all force a system to use context. Regex coverage cannot get past them. These same ambiguities are where English-trained tools are known to fail on Indian text, so a dataset built around them will tell Track 3 teams far more than another clean-text corpus with near-perfect recall.

The second implication is that the scorer matters more than the data. Clinical de-identification benchmarks published to date test neither encoded PHI nor India's specific linkage risk, the relative-name join to the voter roll. A Track 3 scorer that measures recall after decoding, measures residual risk against a simulated electoral roll and penalizes clinical drift would be new evidence in its own right. The open questions it would also have to own are the uniqueness of {age, sex, village} in India, official formats for ABHA display, PMJAY, CGHS and ration cards, and the final ABDM anonymisation threshold. Each should be treated as a labelled policy assumption in the dataset card rather than silently baked into the ground truth.
